This repair changes CI tooling and debug-only YouTube diagnostics. It preserves browser/player behavior, seek controls, mute, ad blocking, and the configured Mây Việt Worker.

Build 165 passed: proxy HTTP/SOCKS and WebSocket tests, five Worker tests, FFmpeg fixture decode, Dart analysis, signed-release compilation, browser discovery/download/playback/landscape, native Media3 and VLC playback, rendered moving frames, mute/volume, tap/autohide, rotation retention, OTA byte/checksum/single-request/reopen tests. The live YouTube test failed, so no release was published.

All emulator suites are mandatory for every release, including browser releases. Signature checks compare apksigner's certificate to the permanent keystore and check the package versionCode. Publication is gated on tests; a draft asset is downloaded and compared before publishing, then the app's latest-release metadata endpoint is checked for tag, size, SHA-256 and APK URL. FFmpeg exists only on CI and is not packaged in the APK.

Build 167 verified the permanent signing certificate and versionCode 167; ARM64 APK size was 33,722,701 bytes. The Emulator host process exited again when downloaded-video preview began. Host memory evidence showed 13 GiB available and no OOM kill. Treating the earlier successful run as proof of stability was insufficient. The next run switches the CI-only software renderer from SwiftShader to Mesa Lavapipe and records/asserts the actual SurfaceFlinger renderer. This remains a hypothesis until the full tests pass. Android documents this supported renderer at https://developer.android.com/studio/run/emulator-acceleration . Gradle dependency caches are saved before runtime tests, so a runtime failure no longer discards all downloaded build dependencies. No signing keys/properties or app data are cached.

Build 168's mandatory renderer check correctly rejected the test environment before video testing: although `-gpu lavapipe` selected Mesa for Vulkan, the emulator log explicitly selected `gles_mode_selected:swangle` and reported a SwiftShader GLES adapter. Switching only the requested renderer label did not eliminate SwiftShader from the path. The next run uses `-gpu host` with Xvfb and Mesa's documented `LIBGL_ALWAYS_SOFTWARE=true` / `GALLIUM_DRIVER=llvmpipe`, retaining the actual-renderer assertion. Xvfb is already installed on the GitHub Ubuntu 24.04 image; no apt mirror dependency is introduced. References: https://docs.mesa3d.org/envvars.html and https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/docs/GPU-EMULATION.TXT .

Build 169 verified actual Mesa llvmpipe GLES. The Emulator stayed alive, but the browser test timed out with Flutter's `_expectingFrame` assertion. The test pumped Flutter for 500 ms immediately after opening a native Activity, which pauses the underlying Flutter surface. That pump can never receive its requested frame while the browser remains open. The next test-harness change removes this rendering wait and uses the existing native-ready polling/assertions; all tab, keyboard, ad, download, preview, rotation and native playback checks remain. Flutter 3.44.4's LiveTestWidgetsFlutterBinding pump implementation explicitly waits for a delivered frame: https://github.com/flutter/flutter/blob/3.44.4/packages/flutter_test/lib/src/binding.dart .

Build 170 passed all browser assertions, Media3/VLC playback clocks and controls, and OTA byte/checksum tests. Pixel verification correctly caught a real VLC freeze: successive screenshots, including after rotation, showed the exact same encoded frame at 5.875 seconds. The plugin registered a Flutter SurfaceTextureEntry and handed the same SurfaceTexture to an Android TextureView, despite using hybrid composition. The next change gives Android's TextureView sole surface ownership, attaches libVLC only when the native surface is ready, and detaches the decoder before surface disposal. Hardware decoding, native controls and all pixel/motion assertions remain enabled.

The live YouTube test again received a sign-in/bot challenge. It remains a failing required test, never a success/skip. Run the original native/OTA/YouTube suite before the browser suite's optional extractor diagnostic, so extractor requests cannot contaminate the ordinary WebView playback baseline. Both suites and all their assertions still run.

The Android suite orchestrator runs both suites even when the first fails, then returns failure if either status is nonzero. This preserves full diagnostics without allowing a failed test to publish an APK.
